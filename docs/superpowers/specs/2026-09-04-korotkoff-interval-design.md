# Детекция интервала тонов Короткова в WAV — дизайн

Дата: 2026-09-04
Статус: согласован

## Задача

По моно-WAV записи измерения артериального давления определить два момента времени:
начало интервала, где слышны удары (тоны Короткова), и его конец. Физически это
моменты систолического и диастолического давления.

Контракт модели: **на входе только аудио**. Канал давления используется исключительно
при обучении как источник меток и при оценке для пересчёта в мм рт. ст.

Выход: `{"start": float, "end": float, "confidence": float}` — секунды от начала файла.

#### Аномалии, найденные сплошной проверкой всех 906 файлов

| Файл | Что не так | Решение |
|---|---|---|
| `recording (221).wav` | 819200 байт нулей, RIFF-заголовка нет | исключить |
| `recording (199).wav` | 17.7% энергии выше 4 кГц, клиппинг, дублирования нет ни при какой фазе | исключить |
| `recording (310).wav` | частота 19200 Гц вместо 16000 | ресемплинг решает |
| `recording (171).wav` | клиппинг до 32768 | пометить, оставить |
| `recording (275).wav` | дублирование нарушено местами (0.918 / 0.344) | пометить, оставить |
| 11 файлов: 117, 136, 223, 311, 322, 333, 344, 1062 и др. | `dup_ratio` по чётным отсчётам 0.17–0.49 | ресемплинг решает |

Про последнюю строку: у этих файлов дублирование цело, но сдвинуто на один отсчёт —
`dup_ratio` по нечётным отсчётам равен 0.99–1.00. Где-то потерян один отсчёт, и
пары сместились.

**Следствие для реализации.** Наивное `x[::2]` — хрупкое решение: оно ломается на
сдвиге пар и не работает для файла на 19200 Гц. Вместо него: приводить любой файл
к общим 8000 Гц через `scipy.signal.resample_poly` с антиалиасным фильтром. Это
корректно независимо от фазы дублирования и от исходной частоты, а весь полезный
сигнал и так лежит ниже 4 кГц.

## Ключевые проверенные факты

Установлено при исследовании данных до написания спеки:

1. Огибающая ударов имеет колоколообразную форму — нарастание, максимум, затухание.
   Пример `recording (100).wav`: амплитуды ударов `0.14 → 0.37 → 0.65 → 0.74 → 0.89 →
   1.00 → 0.89 → 0.71 → 0.28 → 0.12`, интервал примерно 6–17 с.
2. Осциллометрическая огибающая, извлечённая из канала давления, визуально совпадает
   с интервалом ударов в звуке на файлах 100, 599, 1000, 70.
3. Классический детектор на периодичности огибающей работает нестабильно: порог
   приходится подбирать под каждую запись. Это обосновывает обучаемую модель.
4. **Синхронизация аудио↔давление не подтверждена.** Кросс-корреляция модулей
   огибающих дала медианный сдвиг −0.04 с при СКО 2.49 с и корреляции 0.31–0.53.
   Это гипотеза «оба начинаются с нуля, давление пишется дольше», а не факт.

## Компоненты

### `src/audio.py`

Чтение и признаки. Единственное место, где живёт знание о формате.

- Чтение по фактическому размеру, а не по заголовку.
- Приведение к 8000 Гц через `resample_poly` (из 16000 — множитель 1/2,
  из 19200 — 5/12). Не использовать `x[::2]`: см. раздел аномалий.
- Диагностика на каждом файле: `dup_ratio` по чётным и нечётным отсчётам, доля
  энергии выше 4 кГц, доля отсчётов на пределе шкалы. Всё это идёт в манифест,
  файлы за пределами нормы помечаются.
- Полосовой Баттерворт 4-го порядка 20–200 Гц, нулевая фаза (`sosfiltfilt`).
- Кадры: окно 50 мс, шаг 20 мс.
- Признаки, 42 канала:
  - 40 лог-мел полос, диапазон 20–500 Гц
  - RMS-огибающая полосы 20–150 Гц
  - скользящая автокорреляционная оценка периодичности: окно 4 с, максимум
    нормированной автокорреляции огибающей в диапазоне лагов 0.33–1.6 с
    (частота пульса 37–180 уд/мин)
- Нормировка внутри записи (z-score по файлу) — уровень между файлами различается
  в шесть раз, глобальная нормировка это не переживёт.
- Кэш в `data/cache/<номер>.npy`.

### `src/pressure.py`

- Парсинг CSV, интерполяция на равномерные 50 Гц.
- **Отбрасывание первых 2 с** — сброс клапана после накачки даёт ступень, на которой
  полосовой фильтр звенит и забивает полезный сигнал. Проверено: без этого максимум
  осциллограммы всегда ложно попадает на 0.5–1.0 с.
- Осцилляции: полоса 0.7–6 Гц.
- Огибающая: амплитуда **каждой отдельной пульсации** (размах между соседними
  экстремумами), затем интерполяция и сглаживание. Скользящее окно фиксированной
  ширины даёт смазанную огибающую — проверено, не использовать.
- Скорость спуска, начальное и конечное давление — как диагностические признаки
  качества записи.

### `src/sync.py`

Критический этап. Определяет сдвиг между временными осями аудио и давления.

Метод: детектировать моменты отдельных ударов в обоих каналах, сопоставлять
последовательности моментов (не амплитуды — амплитуды коррелируют слабо, проверено).
Оценивать сдвиг сразу по всем 784 файлам: если это аппаратная константа, распределение
оценок даст выраженный пик.

Критерий приёмки: не менее 70% файлов дают согласованную оценку с разбросом
не более ±0.3 с. Если критерий не выполняется — переход к плану Б.

**План Б**, если синхронизация не подтвердится: канал давления как источник меток
отпадает. Остаётся ручная разметка, объём проверки вырастает с ~200 до ~400 файлов,
и автометки заменяются на предсказания классического детектора как затравку.

### `src/autolabel.py`

Два независимых источника, затем согласование.

Из давления: границы по пересечению долей максимума осциллометрической огибающей —
начало на подъёме, конец на спаде. Коэффициенты не брать из литературы, а
калибровать по данным — **но только по калибровочному подмножеству** проверенных
файлов (см. «Разделение проверенных файлов»), иначе коэффициенты подгонятся под тест.

Из звука: детектор периодичности, доведённый до устойчивой работы.

Согласование: расхождение источников больше 1.5 с → файл получает высокий приоритет
в очереди ручной проверки. Проверять сомнительные файлы, а не случайные — при том же
времени человека это даёт больше пользы.

Выход: `data/labels_auto.csv` с колонками
`file, start, end, source_pressure_start, source_pressure_end, source_audio_start,
source_audio_end, disagreement, priority`.

### `tools/make_annotator.py`

Генерирует один автономный HTML-файл, работающий офлайн в браузере.

- Огибающая звука и кривая давления на общей временной оси
- Две вертикальные метки, перетаскиваются мышью
- Воспроизведение с программным усилением (записи тихие)
- Клавиши: `←` `→` переход между файлами, пробел — воспроизведение, `Enter` — принять
- Файлы отсортированы по убыванию `priority`
- Кнопка сохранения отдаёт `labels_verified.csv`

### `src/model.py`

Вход `(T, 42)`, T ≈ 1400 кадров для записи 28 с.

- Свёрточный энкодер: 4 блока `Conv1d(kernel=5) + BatchNorm + GELU`,
  каналы 64 → 64 → 128 → 128, dilation 1 / 2 / 4 / 8.
  Рецептивное поле около 2.5 с — достаточно, чтобы охватить несколько ударов.
- BiGRU, 128 скрытых единиц.
- Линейный слой → 1 логит на кадр.

Около 250 тыс. параметров. Устройство: MPS (Apple M5).

### `src/dataset.py`

- Аугментации: сдвиг по времени, изменение усиления, подмешивание шума из тихих
  участков этих же записей, растяжение времени ±10%.
- Батчи переменной длины через паддинг с маской.

### `src/train.py`

Потери: `BCEWithLogits` со взвешиванием классов плюс Dice-член на предсказанную маску,
чтобы штрафовать рваные предсказания. Ранняя остановка по валидационному IoU.

### Постобработка

1. Медианный фильтр 0.5 с по кривой вероятностей
2. Порог, подобранный по валидации
3. **Закрытие разрывов короче 3 с** — аускультативный провал: у части гипертоников
   тоны пропадают в середине интервала и возвращаются. Интервал — это внешние границы,
   а не сплошная область.
4. Выбор самого длинного интервала
5. Уточнение границ линейной интерполяцией пересечения порога между кадрами

`confidence` — средняя вероятность внутри найденного интервала.

### `src/baseline.py`

Классический детектор без обучения: полосовой фильтр, огибающая, периодичность, порог.
Не вспомогательный код, а полноправная точка сравнения.

### `src/evaluate.py`

Разбиение **непрерывными блоками номеров файлов** 70/15/15. Случайное разбиение
запрещено: соседние номера почти наверняка один испытуемый, и случайное разбиение
даст утечку и завышенную оценку.

Метрики:
- MAE и медиана `|Δt|` отдельно для начала и конца
- Доля попаданий в ±0.5 с и ±1.0 с
- IoU интервала
- Пересчёт границ в мм рт. ст. по кривой давления: средняя ошибка и СКО,
  сравнение с AAMI (средняя ≤5, СКО ≤8 мм рт. ст.)

Отчёт всегда содержит колонку baseline рядом с моделью. Если модель не выигрывает,
это сообщается прямо.

### `src/predict.py`

```bash
python -m src.predict "recording (100).wav"
```
→ `{"start": 6.12, "end": 17.44, "confidence": 0.91}`

## Порядок работ

1. Подготовка данных, манифест, кэш признаков
2. **Синхронизация** ← критическая точка, результат показывается до продолжения
3. Автоматическая разметка
4. HTML-разметчик → ручная проверка ~200 файлов
5. Классический baseline и его оценка
6. Обучение модели
7. Оценка, сравнение с baseline, отчёт

## Риски

| Риск | Последствие | Действие |
|---|---|---|
| Синхронизация не подтвердится | Автометки невозможны | План Б: ручная разметка ~400 файлов |
| 122 файла без давления | Меньше обучающих данных | Ручная разметка или только предсказание |
| Мало уникальных испытуемых | Оценка завышена | Оценить число субъектов по сходству записей, отразить в отчёте |
| Автометки систематически смещены | Модель унаследует смещение | Калибровка коэффициентов по проверенным файлам; проверенные файлы — только в тест |

## Решения, зафиксированные явно

- Модель работает **только по аудио**. Давление при инференсе не требуется.
- Обучение на автометках, **итоговая оценка только на проверенных вручную**.
  Проверенные файлы не попадают в обучение модели.

### Разделение проверенных файлов

Проверенные вручную файлы (~200) делятся на две непересекающиеся части:

- **Калибровочные, ~60 файлов** — на них настраиваются коэффициенты автоматической
  разметки и порог постобработки. Их автометки затем участвуют в обучении наравне
  с остальными.
- **Тестовые, ~140 файлов** — не используются нигде, кроме финальной оценки.
  Ни калибровка коэффициентов, ни подбор порога, ни выбор эпохи их не касаются.

Деление делать блоками номеров, а не случайно, по той же причине, что и основной split.
- Выход — один интервал на запись, а не список отдельных ударов.
- Папка `MultiModal` в задачу не входит.
