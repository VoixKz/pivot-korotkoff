# Демонстрация модели в браузере

Статическая страница: аудиофайл → границы интервала тонов Короткова.
Ни сервера, ни отправки данных — всё считается на стороне клиента.

## Локально

```bash
python3 -m http.server 8792 --directory web
```

Открыть `http://localhost:8792`. Через `file://` не заработает: модули ES
и `fetch` требуют настоящего протокола.

## Публикация на GitHub Pages

Workflow `.github/workflows/pages.yml` публикует содержимое `web/`
при каждом изменении в ветке `main`.

Один раз включить в настройках репозитория: **Settings → Pages → Source →
GitHub Actions**. После этого адрес вида
`https://<пользователь>.github.io/<репозиторий>/`.

## Из чего состоит

| Файл | Назначение |
|---|---|
| `index.html` | Разметка и стили |
| `app.js` | Чтение файла, инференс, отрисовка, плеер |
| `dsp.js` | Признаки — перенос `src/audio.py` на JavaScript |
| `postprocess.js` | Кривая вероятностей → две границы, перенос `src/postprocess.py` |
| `model.onnx` | Модель, 1.4 МБ, экспорт `tools/export_onnx.py` |
| `model_meta.json` | Параметры конвейера и метрика чекпойнта |
| `parity.html` | Численная сверка признаков JS против scipy |
| `reference.json` | Эталон из Python для сверки |
| `sample.wav` | Пример записи для кнопки «Показать на примере» |

Модель считается через ONNX Runtime Web в WebAssembly, библиотека грузится
с jsDelivr.

## Почему WAV разбирается вручную

У записей этого прибора заголовок всегда объявляет 60 секунд, а данных
в файле 33–61%. Браузерный `decodeAudioData` доверяет заголовку и может
дорисовать тишину — границы уедут. Поэтому WAV читается по фактическому
размеру, ровно как `audio.read_wav` при обучении. Прочие форматы (MP3, M4A,
OGG) идут через декодер браузера.

## Сверка признаков

Модель обучалась на признаках из scipy. Если считать их в браузере хоть
немного иначе, на вход придёт другое распределение и предсказания станут
мусором — молча, без ошибки. Поэтому каждый шаг повторяет питоновский
буквально, включая тип паддинга и обработку краёв.

Открыть `parity.html` — он подаёт один и тот же сигнал в обе реализации
и показывает расхождение по этапам. Текущее состояние: не хуже 1e-7
везде, то есть на уровне точности float32.

Сквозная проверка на записи 629: Python даёт `6.621 .. 14.623`,
браузер `6.62 .. 14.63`. Расхождение 0.007 с — меньше половины кадра,
это разница алгоритмов передискретизации.

## Обновление модели

```bash
python -m src.train
python -m tools.export_onnx
```

Экспорт сам сверяет ONNX с PyTorch на трёх длинах записи и печатает
расхождение. Если оно превышает 2e-4, экспорт считать неудачным.

Внимание: экспортёр вызывается с `dynamo=False`. Новый dynamo-путь
игнорирует `dynamic_axes` и зашивает длину примера в граф — модель после
такого экспорта падает на записи любой другой длины.
