# Детекция интервала тонов Короткова

Модель определяет по WAV-записи измерения артериального давления, где начинаются
и где заканчиваются слышимые удары. Физически это моменты систолического и
диастолического давления.

**Вход:** только аудио. **Выход:** два числа в секундах.

```bash
python -m src.predict "recording (100).wav"
```
```json
{"start": 6.12, "end": 17.44, "confidence": 0.91, "duration": 20.0}
```

## Установка

```bash
python3 -m pip install -r requirements.txt
```

Путь к данным задаётся переменной `PIVOT_DATA_ROOT` (по умолчанию
`/Users/BexKex_1/Downloads/Blood pressure raw data 906`). Ожидается структура:

```
<PIVOT_DATA_ROOT>/
├── recording/     recording (N).wav
└── pressure/      pressure N.csv
```

## Порядок работы

```bash
python -m src.manifest              # обход данных, диагностика качества
python -m src.sync                  # проверка синхронности аудио и давления
python -m src.autolabel             # черновые метки по звуку
python -m tools.make_annotator      # HTML для ручной выверки
#   -> разметить, положить data/labels_verified.csv
python -m src.splits                # разбиение + калибровка порогов -> data/thresholds.json
python -m src.autolabel             # перестроить метки с новыми порогами
python -m src.train                 # обучение
python -m src.evaluate              # отчёт
```

Откалиброванные пороги детектора попадают в `data/thresholds.json` и
подхватываются автоматически — править код руками не нужно.

Разметчик открывать через сервер, а не двойным щелчком: Safari блокирует
сохранение прогресса на `file://`.

```bash
python3 -m http.server 8791 --directory data
```

## Что важно знать про данные

Всё это установлено проверками, а не предположениями. Подробности —
в [спецификации](docs/superpowers/specs/2026-09-04-korotkoff-interval-design.md).

**Заголовок WAV врёт.** Все 906 файлов объявляют 60 секунд, а содержат 33–61%.
Читать надо по фактическому размеру файла — этим занимается `audio.read_wav`.

**Частота не постоянна.** 904 файла на 16000 Гц, один на 19200 Гц, у одного
заголовка нет вовсе. Отсчёты продублированы, то есть полезная полоса ≤4000 Гц,
но у 11 файлов дублирование сдвинуто на отсчёт. Поэтому приведение к 8000 Гц
делается через `resample_poly`, а не через `x[::2]`.

**Исключены две записи:** `recording (221).wav` — 819200 байт нулей,
`recording (199).wav` — 17.7% энергии выше 4 кГц при клиппинге.

**Канал давления парный, но не синхронный.** Корреляция длительностей аудио и
давления r = 0.9555 против 0.053 на перемешанных парах — файлы точно от одного
измерения. Но сопоставить их временные оси не удалось: четыре независимые
проверки дали отрицательный результат, в том числе контроль с подстановкой
давления от чужой записи (0.440 против 0.423 — разницы нет). Отчёт:
[reports/sync.md](reports/sync.md).

Отсюда два следствия: метки строятся только по звуку, а метрика в мм рт. ст.
и проверка по стандарту AAMI невозможны.

## Устройство

| Файл | Ответственность |
|---|---|
| `src/config.py` | Все константы конвейера |
| `src/audio.py` | Чтение WAV, приведение к 8 кГц, 42 признака на кадр |
| `src/pressure.py` | Канал давления, осциллометрическая огибающая |
| `src/manifest.py` | Обход данных, диагностика качества |
| `src/sync.py` | Проверка синхронности с контрольным опытом |
| `src/autolabel.py` | Черновые метки, очередь ручной проверки по приоритету |
| `src/splits.py` | Блочное разбиение, калибровка порогов |
| `src/baseline.py` | Классический детектор для сравнения |
| `src/dataset.py` | Dataset, аугментации, паддинг батчей |
| `src/model.py` | CRNN: расширенные свёртки + BiGRU |
| `src/train.py` | Цикл обучения |
| `src/postprocess.py` | Кривая вероятностей → интервал |
| `src/predict.py` | CLI инференса |
| `src/evaluate.py` | Метрики и отчёт |
| `tools/make_annotator.py` | Генератор HTML-разметчика |

**Признаки** (42 канала, шаг 20 мс): 40 логарифмических полос 20–500 Гц,
RMS-огибающая полосы 20–200 Гц, скользящая оценка периодичности.

**Модель:** 4 блока расширенных свёрток (dilation 1/4/8/16, рецептивное поле
2.34 с) → BiGRU 128 → логит на кадр. 356 тыс. параметров.

**Обучение идёт на CPU, а не на MPS,** и это не оплошность. Замер на Apple M5
при батче 8 и длинах как в реальных данных:

| Устройство | мс/шаг |
|---|---|
| MPS, разные длины | 1269 |
| MPS, постоянная длина | 969 |
| CPU, разные длины | **419** |

Модель маленькая, а BiGRU последователен по времени: на запись в 1400 кадров
приходится 1400 мелких запусков ядер, и накладные расходы MPS съедают выгоду
от ускорителя. Разброс длин добавляет ему ещё около 30% на перекомпиляцию под
каждую новую форму тензора. Перекрыть выбор: `python -m src.train --device mps`.

**Постобработка:** медианный фильтр 0.5 с → порог → сшивание разрывов короче 3 с
(аускультативный провал — не конец интервала) → самый длинный участок →
уточнение границ интерполяцией между кадрами.

## Тесты

```bash
python -m pytest -q
```

Тесты, помеченные `data`, требуют доступа к исходным записям и пропускаются,
если данных нет.

## Разбиение выборки

Только непрерывными блоками номеров, никогда случайно: соседние номера файлов
почти наверняка принадлежат одному испытуемому, и случайное деление даёт
утечку между обучением и тестом с завышенной оценкой качества.

Проверенные вручную записи делятся на калибровочные (настройка порогов) и
тестовые (только финальная оценка, больше нигде не участвуют).
